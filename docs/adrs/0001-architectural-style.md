# ADR-0001. Вибір базового архітектурного стилю для ядра системи

## Статус
Accepted

## Контекст
Розроблювана система E-Commerce на початковому етапі має обмежену команду розробників (3-5 осіб), проте передбачає високі вимоги до швидкості виходу на ринок (Time-to-Market) та високі вимоги до модульності коду для можливого подальшого розпилу на мікросервіси. Пряме створення розподіленої мікросервісної інфраструктури на старті призведе до високих витрат на DevOps та ускладнить рефакторинг доменної моделі.

## Рішення
Прийнято рішення використовувати **Модульний Моноліт (Modular Monolith)** із застосуванням принципів **Clean Architecture** (Robert Martin) для внутрішнього устрою кожного модуля.
Всі модулі (Catalog, Order, Payment, Notification) знаходяться у єдиному репозиторії та розгортаються як єдиний артефакт, але суворо ізольовані на рівні коду (кожен модуль має власну доменну модель, Use Cases та чіткі публічні інтерфейси/контракти).

## Розглянуті альтернативи
* **Класичний моноліт (Layered 3-Tier):**
  * *Мінуси:* Ризик перетворення коду у «Велику грудку бруду» (Big Ball of Mud), відсутність суворих меж між доменами.
* **Розподілена мікросервісна архітектура (Microservices):**
  * *Мінуси:* Висока мережева затримка (Network Latency), складність забезпечення розподілених транзакцій (Saga Pattern), високі вимоги до інфраструктури (Kubernetes, Service Mesh) на ранній стадії.

## Наслідки
* **Позитивні:**
  * Швидка розробка та спрощене логічне відлагодження в єдиному процесі.
  * Легке написання юніт- та інтеграційних тестів.
  * Можливість безболісного виділення будь-якого модуля в окремий мікросервіс у майбутньому без зміни бізнес-логіки.
* **Негативні / Компроміси (Trade-offs):**
  * Необхідність суворого контролю Code Review, щоб розробники не імпортували внутрішні класи інших модулів прямими шляхами.
