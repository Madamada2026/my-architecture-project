# ADR-0003. Вибір архітектури автентифікації та авторизації

## Статус
Accepted

## Контекст
Необхідно забезпечити безпечний, масштабований та стандартний механізм автентифікації для веб-клієнтів, мобільних додатків та зовнішніх інтеграцій із підтримкою підписування токенів та контролю прав доступу (RBAC).

## Рішення
Прийнято рішення застосувати протокол **OAuth 2.0 / OpenID Connect (OIDC)** із використанням **JWT (JSON Web Tokens)**.
Для керування обліковими записами використовується готове рішення **Keycloak (Identity Provider)**.

## Розглянуті альтернативи
* **Сесійна автентифікація на основі Stateful Cookies:**
  * *Мінуси/Чому відхилено:* Погано масштабується горизонтально (потребує загального СУБД/Redis сховища сесій для всіх нод) та не підходить для мобільних додатків.
* **Власна самописна система автентифікації:**
  * *Мінуси/Чому відхилено:* Високий ризик припущення помилок у безпеці, додаткові витрати часу на розробку.

## Наслідки
* **Позитивні:**
  * Stateless-автентифікація: мікросервіси/модулі можуть перевіряти підпис JWT самостійно без додаткових запитів до БД.
  * Відповідність сучасним стандартам безпеки.
* **Негативні / Компроміси (Trade-offs):**
  * Неможливість миттєвого відкликання Access Token до закінчення терміну його дії (вирішується коротким TTL token = 15 хв та Refresh Tokens).
