### 1. Вступ та цілі системи
**E-Commerce Cloud Platform** — це хмарна високонавантажена платформа онлайн-торгівлі. 
Головні цілі:
1. Забезпечити можливість одночасної обслуги понад 100 000 активних користувачів у період пікових продажів.
2. Скоротити час обробки замовлення від кліка до передачі в службу доставки до < 2 секунд.
3. Забезпечити високу доступність системи (SLA 99.9%).

### 2. Архітектурні обмеження та NFR (ISO 25010)
| Категорія (ISO 25010) | Конкретизована нефункціональна вимога | Метрика |
| :--- | :--- | :--- |
| **Performance Efficiency** | Швидкість пошуку та видачі результатів у каталозі товарів. | Latency p95 ≤ 150 ms при навантаженні 1 000 RPS. |
| **Performance Efficiency** | Пропускна здатність системи під час пикових розпродажів. | 3 000 RPS створення замовлень без помилок 5xx. |
| **Reliability** | Безперервна доступність сервісів маркетплейсу. | SLA = 99.9% (простій не більше 8.76 годин на рік). |
| **Maintainability** | Покриття бізнес-логіки автотестами. | Покриття доменної логіки (Domain/Use Cases) юніт-тестами ≥ 80%. |
| **Flexibility** | Горизонтальне масштабування компонентів. | Автомасштабування контейнерів при споживанні CPU > 70% протягом 2 хв. |

### 3. Контекст та межі системи (C4 Level 1)
Система взаємодіє з такими зовнішніми акторами та сервісами:
* **End User (Покупець)** — взаємодіє через SPA/Mobile App по HTTPS.
* **Administrator** — керує каталогом товарів.
* **External Payment Gateway (LiqPay/Stripe)** — обробка платежів.
* **Delivery System (Nova Poshta)** — оформлення ТТН.
*(Детальна C4-діаграма знаходиться у `docs/architecture_diagrams_report.md`)*

### 4. Архітектурна стратегія та ADR
Для побудови системи обрано **Модульний моноліт (Modular Monolith)** із застосуванням **Clean Architecture**.
Ключові рішення (ADR):
* **[ADR-0001]** Вибір базового архітектурного стилю.
* **[ADR-0002]** Стратегія баз даних (PostgreSQL + Redis).
* **[ADR-0003]** Архітектура автентифікації (OAuth 2.0 / OIDC).
* **[ADR-0004]** Топологія розгортання (Docker Single-Node).
*(Повні тексти ADR знаходяться у папці `docs/adrs/`)*

### 5. Структурні діаграми
* **C4 Level 2 (Контейнери):** Складається з API Gateway (Nginx), Order Service (.NET), Identity Provider (Keycloak), Бази даних (PostgreSQL) та Redis.
* **UML Class Diagram:** Основні сутності предметної області: `User`, `Product`, `Order`, `OrderItem`, `Payment`, `ShippingAddress`.
* **UML Component Diagram:** Відображає модулі всередині моноліту (Order, Catalog, Payment).
*(Детальні діаграми знаходяться у `docs/architecture_diagrams_report.md`)*

### 6. Динаміка взаємодії
* **Створення замовлення:** Клієнт відправляє POST-запит. `CreateOrderUseCase` (Application) перевіряє дані, зберігає замовлення через репозиторій і публікує подію `OrderCreatedEvent` в In-Memory шину.
* **Асинхронна обробка події:** Шина викликає двох незалежних споживачів: `InventoryConsumer` (резервує товар) та `NotificationConsumer` (відправляє email).
* **API Контракти:** REST API описано в `api/openapi.yaml`, gRPC-контракти в `api/service.proto`. Забезпечено ідемпотентність споживачів через збереження `EventId`.

### 7. Фізична архітектура (UML Deployment Diagram)
Система розгортається в середовищі Docker (Single-Node).
* **Вузол (Device):** Cloud VM / Локальний ПК розробника.
* **Середовище виконання (Execution Environment):** .NET Runtime (всередині Docker-контейнера).
* **Артефакти:** `WebAPI.dll` (містить API, Use Cases, Domain та In-Memory Bus), файли конфігурації `appsettings.json`.
* **Протоколи:** HTTPS (від клієнта до API), TCP (до БД).
*(Детальна діаграма знаходиться у `docs/diagrams/deployment_diagram.md`)*

### 8. Компроміси та ризики
* **Компроміс:** Використання In-Memory шини замість RabbitMQ/Kafka. 
  * *Плюс:* Нульова затримка мережі, легкість розгортання.
  * *Мінус:* При падінні процесу WebAPI всі необроблені повідомлення втрачаються.
* **Ризик:** Модульний моноліт може перетворитися на "Big Ball of Mud", якщо розробники почнуть порушувати межі модулів.
